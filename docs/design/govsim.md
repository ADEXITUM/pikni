# Проект имитатора смежных систем govsim

Документ детализирует п. 4.2.12 ТЗ ([tz.md](../tz.md)) и является описанием протокола имитатора по разделу 9 ТЗ. Сторона «Пикни» (адаптеры, обмен сообщениями) описана в [backend.md](backend.md), п. 4.

## 1 Назначение и границы

`govsim` изображает для учебного стенда три внешние стороны, без которых алкомаркет не работает:

| Сторона | Что изображает | Что не изображает |
|---|---|---|
| ЕГАИС с УТМ точек | Остатки по регистрам склада и зала, учёт марок, документы и квитанции, проверку чека с марками | XML-схемы, электронную подпись, реальные идентификаторы ЕГАИС, декларирование |
| ГИС МТ «Честный знак» | Реестр кодов пива и воды, владельца, срок годности, блокировки; проверку кода перед продажей (разрешительный режим) и выбытие | Заказ и нанесение кодов, ЭДО и УПД, ОФД, локальный модуль |
| Поставщик | Отгрузку по ТТН с марками и упаковками, расхождения по сценарию, печать марок и этикеток | Договоры, оплату, логистику |

Главное отличие от заглушки — **имитатор хранит состояние**. Он знает, какие марки числятся у какой точки, какие проданы, сколько пива на регистре зала. Поэтому проверки работают по-настоящему: вторая продажа одной марки отклоняется, акт списания пива сверх остатка отклоняется, а сверка находит реальные расхождения.

**Все данные вымышлены:**
- марки генерируются с префиксом `PKN` и не совпадают с настоящими;
- GTIN берутся из диапазона внутреннего использования;
- ФСРАР ID учебных участников начинаются с `0300000000`.

Названия типов документов взяты «по мотивам» обмена ЕГАИС, чтобы сценарии были узнаваемы. Структура документов упрощена и задаётся этим проектом.

## 2 Устройство

- **Модуль.** Отдельный модуль Go в каталоге `govsim/` со своим `go.mod`: с кодом «Пикни» он ничего не разделяет. Исполняемый файл `govsim` с подкомандами `serve`, `migrate`, `seed`.
- **База** — `govsim` на том же сервере PostgreSQL, отдельный пользователь.
- **Интерфейс** — простой веб-интерфейс на шаблонах Go (`html/template`) без сборки фронтенда: таблицы, формы, переключатели.
- **Доступ.** API для «Пикни» доступен только во внутренней сети Docker. Веб-интерфейс опубликован через Caddy по адресу `/govsim/` с отдельным паролем администратора стенда.

### 2.1 Таблицы

| Таблица | Ключевые поля |
|---|---|
| `participants` | `fsrar_id` (PK), `inn`, `kpp`, `name`, `kind` (supplier, retail_point, warehouse), `address` |
| `products` | `alcocode` (PK), `name`, `kind_code`, `volume_l`, `abv`, `producer`, `egais_accounting` (marked, quantity) |
| `marks` | `code` (PK), `alcocode`, `owner_fsrar`, `status` (in_transit, on_balance, sold, written_off), `package_code`, `ttn_id`, `updated_at` |
| `rests` | PK (`fsrar_id`, `alcocode`, `register`), `qty` — регистры 1 (склад) и 2 (торговый зал) для продукции без марок |
| `packages` | `code` (PK), `parent_code`, `ttn_id` — короба и палеты в ТТН |
| `documents` | `id` (PK), `fsrar_from`, `fsrar_to`, `type`, `payload` jsonb, `status` (received, accepted, rejected), `reject_reason`, `created_at` |
| `outbox` | `id` (PK), `fsrar_id` (кому), `type`, `payload` jsonb, `created_at`, `acked_at` — «исходящие УТМ» для каждого участника: ТТН, квитанции, ответы |
| `cheques` | `id`, `fsrar_id`, `marks` text[], `qr_url`, `created_at`, `kind` (sale, return) |

| `scenarios` | `fsrar_id`, `utm_down`, `delay_ms`, `blocked_marks` text[], `expired_batches` text[] |

## 3 Протокол ЕГАИС (УТМ точки)

Базовый адрес УТМ точки: `/utm/{fsrar_id}`. Обмен асинхронный, как в настоящем УТМ: документ отправляется во «входящие» ЕГАИС, ответ и квитанция появляются в «исходящих» участника.

| Метод | Назначение |
|---|---|
| `GET /utm/{fsrar}/status` | Состояние УТМ. При включённом сценарии «УТМ недоступен» все методы УТМ точки отвечают 503 |
| `POST /utm/{fsrar}/opt/in/{type}` | Отправить документ. Ответ — `{"reply_id": "..."}` сразу; результат придёт квитанцией |
| `GET /utm/{fsrar}/opt/out` | Список сообщений для точки: ТТН от поставщиков и других точек, квитанции, ответы на запросы |
| `GET /utm/{fsrar}/opt/out/{id}` | Получить сообщение |
| `DELETE /utm/{fsrar}/opt/out/{id}` | Подтвердить обработку (удалить из «исходящих») |
| `POST /utm/{fsrar}/cheque` | Синхронно: чек с марками. Ответ — QR-ссылка и подпись или отказ с причиной |

### 3.1 Типы документов

| Тип | Кто отправляет | Что делает имитатор |
|---|---|---|
| `WayBill` | поставщик (генератор), точка при перемещении или возврате | Марки переходят в `in_transit`, количество продукции без марок списывается с регистра 1 отправителя. Получателю в «исходящие» кладётся ТТН |
| `WayBillAct` | получатель ТТН | Акт подтверждения: марки → `on_balance` у получателя, количество → регистр 1. Акт расхождения: принятое — получателю, остальное возвращается отправителю. Отправителю — копия акта, получателю — квитанция |
| `TransferToShop`, `TransferFromShop` | точка | Перевод количества между регистрами 1 и 2. Отказ при нехватке |
| `ActWriteOff` | точка | Списание со склада: марки → `written_off`, количество с регистра 1 |
| `ActWriteOffShop` | точка | Списание из зала, в том числе с причиной «Реализация» для пива. Отказ при нехватке на регистре 2 |
| `ActChargeOn` | точка | Постановка на баланс (излишки ревизии): марки → `on_balance`, количество → регистр |
| `QueryRests` | точка | Ответ `ReplyRests`: остатки по регистрам 1 и 2 и список марок на балансе |
| `Ticket` | имитатор | Квитанция по документу: `accepted` или `rejected` с причиной |

### 3.2 Чек

`POST /utm/{fsrar}/cheque`:

```json
{ "kind": "sale", "receipt_id": "0193…", "marks": ["PKN…", "PKN…"], "datetime": "2026-11-10T19:12:44+09:00" }
```

| Проверка | Причина отказа |
|---|---|
| Марка существует | `mark.unknown` |
| Владелец — эта точка, статус `on_balance` | `mark.not_on_balance` |
| Не продана ранее | `mark.already_sold` |
| Не заблокирована сценарием | `mark.blocked` |

- **При успехе** марки получают статус `sold`, ответ содержит `qr_url` вида `https://govsim…/check/{id}` (страница «чек проверен в ЕГАИС») и подпись-заглушку.
- **Чек возврата** (`kind: return`) возвращает марки в `on_balance`.
- **Повтор** чека с тем же `receipt_id` возвращает прежний ответ.

## 4 Протокол ГИС МТ

| Метод | Назначение |
|---|---|
| `POST /crpt/codes/check` | `{"codes": [...]}` → для каждого кода `allowed`, `reason` (`code.unknown`, `code.sold`, `code.blocked`, `code.expired`, `code.not_owner`), `expires_at` |
| `POST /crpt/sales` | Выбытие проданных кодов (в жизни — через ККТ и ОФД). Повтор безопасен |
| `POST /crpt/returns` | Возврат кода в оборот при возврате покупателем |

Владелец кодов пива меняется на получателя, когда имитатор ЕГАИС принимает акт подтверждения по ТТН с этим пивом. Так упрощённо изображается переход права собственности по УПД.

## 5 Генератор поставок и сценарии

### 5.1 Демо-поставка (ИС-4)

Форма в веб-интерфейсе и метод `POST /supplier/shipments`:
- **Получатель** — точка, **поставщик** — один из учебных.
- **Состав:** позиции и количество или «случайная поставка на N позиций».
- **Упаковка:** по 6 или 12 бутылок в коробе, короба на палете.
- **Расхождения:** недостача N единиц, излишек N единиц, пересорт (вместо позиции X положена Y), чужая марка (марка, которой нет в ТТН), повреждённая марка.

Генератор создаёт марки и коды «Честного знака», отправляет ТТН в «исходящие» получателя и готовит печатную страницу. На ней марки (PDF417 или DataMatrix), штрихкоды товаров и этикетки коробов, разложенные по коробам с учётом заложенных расхождений. Страницу можно распечатать на А4 или сохранить в PDF средствами браузера, а можно сканировать прямо с экрана.

### 5.2 Сценарии (ИС-5)

| Сценарий | Что происходит |
|---|---|
| УТМ точки недоступен | Все методы УТМ точки отвечают 503: касса не продаёт продукцию с марками, сообщения копятся в очереди «Пикни» |
| Задержка ответа | Ответы и квитанции приходят с задержкой N секунд |
| Марка заблокирована | Указанные марки отклоняются при продаже и перемещении |
| Партия пива просрочена или отозвана | Коды партии отклоняются при проверке с причиной `code.expired` или `code.blocked` |
| Расхождение для сверки | Изменить остаток или статус марки у точки, чтобы сверка «Пикни» его нашла |

### 5.3 Страницы веб-интерфейса

- **Участники** — точки и поставщики, состояние УТМ, переключатели сценариев.
- **Остатки точки** — регистры 1 и 2, марки на балансе.
- **Марка** — история: ТТН, акты, чек.
- **Журнал** — документы и квитанции с фильтрами.
- **Новая поставка** — генератор (п. 5.1).
- **Проверка кода «Честного знака»** — статус, владелец, срок годности.

## 6 Согласованность с «Пикни»

Демонстрационные данные создаются одним генератором `pikni seed`, который заполняет обе базы через их API и миграции. Остатки и марки при старте совпадают, кроме заранее заложенных расхождений для сверки. Ежесуточный сброс стенда восстанавливает обе базы из согласованных эталонных дампов.
