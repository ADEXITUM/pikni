# Вопросы к защите

Вероятные вопросы комиссии и короткие ответы. Пополняется в конце каждой итерации. Подробности — в [журнале решений](decisions/README.md).

## Границы работы

**Зачем системе учёта касса?**
Продажа — основной расход товара. Без неё остаток никогда не уменьшается, акт списания проданного пива для ЕГАИС не из чего сформировать, а сверка с ЕГАИС показывает расхождение по каждой проданной бутылке: ЕГАИС считает её проданной, учёт — стоящей на полке. В сетях касса обычно отдельная программа, которая обменивается с учётной системой: получает товары, цены и ограничения, отдаёт чеки. Поэтому сервер принимает продажи через кассовый API, а учебная касса — его клиент: она не обращается к базе напрямую и показывает, что этого API хватит любой кассовой программе. Фискализация по 54-ФЗ в рамки работы не входит: чек учебный.

**Почему остатки товаров без марок не сверяются с государственными системами?**
Сверять не с чем: их остатки знает только сама сеть, поэтому их проверяет ревизия. Остатки алкоголя с марками знает ЕГАИС — по каждой точке и каждой марке, поэтому для него есть и ревизия, и сверка. Расхождения возникают на практике постоянно: пробили одну бутылку, а отдали другую, бой не списали, возврат провели мимо ЕГАИС. Расхождение баланса ЕГАИС с фактом — нарушение порядка учёта (ст. 14.19 КоАП), поэтому сверка автоматизирована.

**Почему нет страницы наличия для покупателей?**
Она не относится к учёту: ни сканера, ни отчётов в ней нет. Поиск наличия по сети есть во внутреннем приложении — по нему продавец отвечает покупателю. Публичная страница потянула бы вопросы о рекламе алкоголя в интернете (ст. 21 закона 38-ФЗ), не связанные с темой, поэтому она в перспективах развития. Решение 0028.

## Итерация 0. Архитектура и «ходячий скелет»

**Почему не микросервисы?**
Проведение документа должно одновременно изменить остатки, марки и очередь в ЕГАИС — это одна транзакция базы данных. В микросервисах это распределённая транзакция с сагами и компенсациями. При нашей нагрузке (десятки пользователей) и одном разработчике это сложность без выгоды. Модули разделены так, что любой можно выделить в сервис позже. Решение 0001.

**Почему Go?**
Сервер — один исполняемый файл, Docker-образ весит десятки мегабайт, памяти нужно мало. Горутины дёшевы, поэтому тысячи одновременных соединений (кассы, WebSocket) не проблема. Решение 0002.

**Почему PostgreSQL, а не MongoDB?**
Учёт требует транзакций: остатки, марки и документы меняются вместе. Гибкость схемы нужна только для характеристик товаров, и её даёт поле JSONB с индексом. Вторая база добавила бы проблему согласованности. Решение 0003.

**Почему нет Kafka или RabbitMQ?**
Событий у нас десятки в секунду. Очередь River хранит задачи в той же PostgreSQL, поэтому задача ставится в той же транзакции, что и данные. С отдельным брокером запись в базу и отправка сообщения не атомарны, понадобились бы паттерн outbox и ретранслятор. Решение 0003.

**Что такое контракт API и зачем генерация кода?**
`openapi/pikni.yaml` описывает все методы, параметры и ответы. Из него генерируются интерфейс сервера на Go и типы клиента на TypeScript. Если изменить контракт и забыть поправить код, проект не скомпилируется — ошибка видна до запуска. CI проверяет, что сгенерированный код совпадает с контрактом. Решение 0004.

**Почему sqlc, а не ORM?**
SQL пишется явно, его можно показать и объяснить. sqlc проверяет запросы по схеме базы при генерации: опечатка в колонке видна сразу. ORM скрывает SQL, и ошибки проявляются уже во время работы. Решение 0005.

**Что такое миграции и почему без отката?**
Миграция — пронумерованный SQL-файл, который меняет схему. Программа помнит, какие уже применены, и применяет только новые, поэтому схема одинакова везде. Откат схемы на рабочем сервере опасен, поэтому ошибку исправляют новой миграцией, а миграции пишут совместимыми с предыдущей версией приложения. Решение 0006.

**Чем /healthz отличается от /readyz?**
`/healthz` — «процесс жив», по нему Docker решает, перезапускать ли контейнер. `/readyz` — «готов обслуживать», включает проверку базы. Если база недоступна, перезапуск сервера не поможет, поэтому `/healthz` остаётся 200, а `/readyz` отвечает 503, и прокси перестаёт слать запросы этой копии.

**Почему нет ошибок CORS?**
Браузер обращается к одному адресу: при разработке — к Vite, на сервере — к Caddy. Тот отдаёт статические файлы и пересылает `/api` на Go внутри сети Docker. Для браузера страница и API — один источник (origin), поэтому CORS не возникает, а Go наружу не открыт.

**Почему Vue без SSR, а не Nuxt, как в курсовой?**
SSR нужен публичным сайтам для поисковых систем и быстрой первой загрузки. Складская система внутренняя, поэтому достаточно SPA: после сборки это статические файлы, сервер Node.js не нужен. Решение 0009.

**Почему не PrimeVue?**
С версии 5 у PrimeVue коммерческая лицензия с ключом. Бесплатный тариф не подходит компании больше чем на 10 сотрудников, а у учебного заказчика их 33. Это противоречит требованию ТЗ использовать только свободное ПО. Vuetify распространяется под MIT. Решение 0009.

**Что такое OpenTelemetry и что даёт трассировка?**
Это открытый стандарт сбора трассировок, метрик и журналов. Трассировка показывает путь одного запроса: HTTP-обработчик → SQL-запрос → взятие соединения из пула, с длительностью каждого шага. По `trace_id` из трассировки находятся строки журнала этого запроса. Стандарт не привязан к поставщику: хранилище меняется настройкой. Решение 0010.

**Почему не Kubernetes?**
Он рассчитан на десятки сервисов на нескольких серверах, ему нужно минимум три узла и отдельное сопровождение. У нас один сервер. Docker Compose умеет запускать несколько копий сервера, а контейнеры без состояния переносятся в Kubernetes без изменения кода, если сеть вырастет. Решение 0008.

**Почему UUIDv7, а не автоинкремент?**
UUIDv7 упорядочен по времени, поэтому индексы растут последовательно, как у автоинкремента. Его безопасно показывать в адресах: по нему нельзя посчитать число записей. И его может создать сам клиент — это нужно сканам и чекам, созданным без связи, чтобы повторная отправка не дала дубль. В PostgreSQL 18 есть встроенная `uuidv7()`.

## Итерация 1. Вход, права, журнал действий

**Почему сессии, а не JWT?**
JWT удобен, когда токен проверяют разные сервисы без общей базы. У нас один сервер и одна база, а отозвать JWT до истечения срока нельзя без списка отозванных — то есть без той же базы. Сессия в таблице отзывается удалением строки: блокировка сотрудника действует со следующего запроса. Токен лежит в cookie HttpOnly, поэтому скрипт на странице его не прочитает, а в базе хранится только его хеш. Решение 0014.

**Почему своя аутентификация, а не Keycloak?**
Keycloak бесплатен, но это отдельный Java-сервис с базой и около гигабайта памяти; единый вход нужен, когда приложений много, а у нас одно. Своя реализация собрана из стандартных примитивов — Argon2id, криптографический генератор, сравнение за постоянное время — и покрыта тестами на каждое правило. Решение 0015.

**Почему Argon2id, а не SHA-256?**
SHA-256 видеокарта считает миллиарды раз в секунду, перебор слабых паролей занимает минуты. Argon2id требует 19 МиБ памяти на каждую попытку, поэтому параллельный перебор упирается в память. Соль своя у каждого пароля, параметры записаны в самом хеше и могут быть повышены без сброса паролей.

**Как защищён вход от подбора пароля?**
Три меры. После 5 ошибок подряд вход в учётную запись закрывается на 15 минут — это хранится в базе и общее для всех копий сервера. С одного IP — не больше 10 попыток в минуту. Для несуществующего логина хеш всё равно вычисляется, чтобы по времени ответа нельзя было узнать, какие логины существуют. Сообщение об ошибке одинаковое для неверного логина и пароля.

**Что такое CSRF и как вы от него защищаетесь?**
Чужой сайт может отправить форму на наш адрес, и браузер сам приложит cookie сессии. Защита двойная: сервер отклоняет изменяющие запросы с чужих сайтов по заголовкам `Sec-Fetch-Site` и `Origin`, которые страница подделать не может, а кроме того требует заголовок `X-CSRF-Token`, который знает только наш клиент. Решение 0021.

**Почему журнал действий нельзя изменить?**
Приложение подключается к базе отдельной ролью без права изменять и удалять записи журнала — база отвечает «нет прав». Сверх того, триггер отклоняет изменение даже для владельца таблиц. Тесты проверяют оба слоя. Решение 0016.

**Как устроены права? Где их проверяют?**
Каждая операция в контракте API указывает нужное право (`x-permission`); сервер читает их при запуске и не запустится, если право забыто. Матрица «роль → право → охват» повторяет таблицу ТЗ: «+» и «П» — вся сеть, «Т» — свои точки. Списки фильтруются по точкам прямо в SQL, а точку, присланную клиентом, проверяет сервер. Клиент получает список прав только чтобы не показывать лишние кнопки. Решение 0018.

**Что будет, если два администратора одновременно редактируют сотрудника?**
Форма отправляет версию, с которой открылась карточка. Сервер блокирует строку на время транзакции и сравнивает версию; если её уже изменили, отвечает 409, и второй администратор видит сообщение, а не затирает чужие правки молча. Это оптимистическая блокировка. Решение 0019.

**Как журнал не расходится с данными?**
Запись в журнал делается в той же транзакции, что и само изменение: либо сохраняются оба, либо ничего. Тест создаёт сотрудника с занятым логином — транзакция откатывается вместе с записью журнала. Решение 0020.

**Как вы тестируете работу с базой?**
Интеграционные тесты поднимают настоящий PostgreSQL в Docker. Миграции применяются один раз к шаблону, а каждый тест получает свою копию базы за десятки миллисекунд, поэтому тесты независимы и идут параллельно. Так проверяются ограничения, триггеры, права ролей и транзакции — то, что не поймает подмена базы. Решение 0017.

## Итерация 2. Нормативно-справочная информация

**Почему правила продажи алкоголя — справочник, а не код?**
Время продажи задают федеральный закон и законы субъектов, и они меняются. В справочнике каждая редакция — строка с датой начала, поэтому новый закон вносится через экран, а прошлые правила остаются для истории. Проверка — чистая функция от правил, дней запрета и местного времени точки: тест подставляет любой момент и проверяет граничные минуты. Часам кассы не доверяем — время берётся на сервере по часовому поясу точки. Решение 0022.

**Почему характеристики хранятся в JSONB, а не в отдельной таблице или MongoDB?**
Набор характеристик зависит от категории, и заводить колонку на каждую нельзя. Таблица «позиция — характеристика — значение» требует соединения на каждый фильтр и теряет типы. MongoDB — вторая СУБД и потеря общей транзакции с остатками и документами. В JSONB значения лежат рядом с позицией, индекс GIN ускоряет фильтры, а схема категории описывает допустимые характеристики: сервер не примет лишнюю, значение не того типа или вне списка. Решение 0023.

**Как гарантируется, что у позиции бренд именно её производителя?**
Составным внешним ключом: пара (бренд, производитель) позиции должна существовать в таблице брендов. Так же линейка привязана к бренду, а регион — к стране. Это проверяет база, поэтому правило не обойти ни импортом, ни ручным SQL; сервис только переводит нарушение ограничения в понятное сообщение. Решение 0024.

**Как найти товар по скану марки ЕГАИС?**
В марке старого образца (штрихкод PDF417, 68 символов) символы с 8-го по 19-й — алкокод в системе счисления по основанию 36; сервер переводит его в 19 цифр и ищет вариант с таким алкокодом. Из кода «Честного знака» берётся GTIN после (01). В марке нового образца (150 символов) алкокода нет — товар по ней находится только по документам приёмки, и экран так и сообщает. Сканер работает как клавиатура, поэтому сервер снимает служебные префиксы и исправляет буквы, набранные в русской раскладке. Решение 0025.

**Почему артикул у варианта, а не у позиции?**
Артикул называет то, что стоит на полке. В алкогольной рознице каждый объём — отдельный товар со своей ценой и своим кодом продукции в ЕГАИС, как в одежде у каждого цвета свой артикул. Позиция только группирует общие данные: наименование, производителя, характеристики. Сначала артикул был у позиции, и у трёх бутылок разного объёма был один номер; миграция перенесла его на варианты и пронумеровала уже заведённые. Решение 0031.

**Почему полнотекстовый поиск PostgreSQL, а не LIKE или Elasticsearch?**
`LIKE '%…%'` не знает морфологию и не использует обычный индекс. Полнотекстовый поиск с конфигурацией `russian` находит «водка» по «водки», каждое слово ищется с начала, а индекс GIN по вычисляемой колонке делает это быстро. Elasticsearch — отдельный сервис и синхронизация данных, а каталог сети в тысячи позиций PostgreSQL обслуживает сам. Решение 0025.

**Почему деньги хранятся в копейках?**
Числа с плавающей точкой хранят дроби приближённо: 0,1 + 0,2 не равно 0,3. В приложении цена — целое число копеек, в базе — `numeric(12,2)`, чтобы суммы в отчётах считались прямо в SQL. МРЦ тоже считается в целых копейках с округлением вверх. Решение 0026.

**Как система не даёт продать дешевле минимальной цены?**
МРЦ устроена как в приказах Минфина: для группы продукции и полосы крепости «свыше 40 до 41 %» задана цена за 0,5 литра, для другого объёма она пересчитывается пропорционально, а водка в таре от 0,375 до 0,5 литра стоит как 0,5. Розничную цену ниже МРЦ сервер не принимает, касса проверит её при продаже. Если МРЦ подняли после назначения цены, карточка подсвечивает «ниже МРЦ». Первая версия пересчитывала цену пропорционально крепости — проверка текстов приказов показала полосы, и модель исправлена новой миграцией. Решение 0026.

**Как импорт «всё или ничего» показывает ошибки сразу во всех строках?**
Импорт идёт в одной транзакции, а каждая позиция — в своей точке сохранения: ошибка откатывает только эту позицию, и проверка продолжается. В конце транзакция фиксируется, только если ошибок нет. Предпросмотр — тот же прогон, который всегда откатывается, поэтому он проверяет ровно то же, что ручной ввод: МРЦ, характеристики, связи бренда и производителя. Решение 0027.

## Итерация 3. Сканер

**Как отличить аппаратный сканер от человека, если оба «печатают»?**
Сканер в режиме клавиатуры вводит символы с интервалом в единицы миллисекунд и заканчивает Enter, человек печатает с паузами 80–200 мс. Обработчик слушает клавиатуру на всём экране: если между символами меньше 35 мс, символов не меньше шести и в конце Enter — это скан, а символы, попавшие в поле ввода, убираются. Поэтому скан работает без фокуса в поле, а обычный набор в поиске сканом не считается (П-19).

**Почему коды распознаёт ZXing на WebAssembly, а не встроенный в браузер BarcodeDetector?**
BarcodeDetector есть в Chrome на Android, но его нет в Chrome на Windows и в Safari на iPhone, а разделители в кодах «Честного знака» разные платформы отдают по-разному. ZXing-C++, собранный в WebAssembly, работает одинаково везде, и его проверяют автоматические тесты на настоящих изображениях кодов. Решение 0029.

**Зачем распознавать в отдельном потоке и только под рамкой?**
Распознавание кадра занимает десятки миллисекунд, и в основном потоке интерфейс подтормаживал бы. В фоновом потоке (Web Worker) интерфейс остаётся плавным, а пока поток занят, новые кадры пропускаются. Рамка работает как прицел: на полке десяток бутылок, читается та, на которую навели камеру, и пикселей обрабатывается меньше.

**Почему камера требует HTTPS?**
Браузер даёт доступ к камере только в защищённом контексте — на HTTPS или localhost. Поэтому стенд работает по HTTPS (итерация 12), а если страницу открыли по HTTP, экран объясняет, в чём дело.

**Как камера не считает одну бутылку десять раз?**
Код виден в каждом кадре, поэтому повтор того же кода в течение 2 с гасится, а пока код в кадре, окно продлевается (СК-2). Ручной ввод не гасится: его человек повторяет намеренно. Ошибочный скан можно отменить, и тогда тот же код принимается сразу.

**Зачем звуки, если есть экран, и почему они синтезируются?**
Продавец смотрит на бутылку, а не на телефон. Исход скана передаётся четырьмя каналами — звуком, вибрацией, цветом и словом со значком, — потому что любой из них может быть недоступен: шум в зале, iPhone без вибрации, плохое различение цветов. Смысл несёт ритм: «ток» — принято, «ток-пум» — проверьте, «пум-пум» — не найдено, длинный «пум» — стоп. Звуки синтезируются Web Audio API: нет файлов, лицензий и задержки загрузки. Решение 0030.

**Как проверяли камеру без телефона?**
Двумя способами. Тесты рисуют коды тем же ZXing — EAN-13, SSCC, код «Честного знака», марку PDF417, QR — и читают их с настройками камеры: так видно, что код доходит до разбора без искажений. Весь путь от камеры до карточки товара проверен в Chromium, которому вместо камеры подставлено видео с кодами (флаги `--use-fake-device-for-media-stream` и `--use-file-for-fake-video-capture`).

## Обзор после итерации 3

**Зачем системе средняя себестоимость и что с отрицательными остатками?**
Учёт ТМЦ ведётся не только в штуках, но и в деньгах: ведомость остатков и оборотная ведомость в рублях, себестоимость продаж для наценки, суммы в актах списания и сличительной ведомости. Себестоимость считается по средней взвешенной в целом по сети — этот способ допускает ФСБУ 5/2019. Отрицательный остаток (продажа товара без марок сверх учёта) в среднюю не входит: приход при нулевом или отрицательном остатке задаёт среднюю ценой прихода, иначе формула даёт цену выше любой закупки или деление на ноль. Правило записали до того, как появился регистр.

**Почему импорт спрашивает про каждое отличие от каталога?**
Импорт обновляет и прайс, а опечатка в файле не должна молча менять цену. Позиция уникальна по паре «производитель + наименование», поэтому повторная загрузка находит её, а не создаёт дубль; каждое отличие — поле позиции, код или цена — показывается «в каталоге / в файле», и пользователь выбирает, что оставить, как при разрешении конфликтов слияния. Сервер между шагами ничего не хранит: на загрузку уходит тот же файл со списком принятых отличий. Решение 0033.

**Не мешают ли подтверждения на каждое изменение?**
Это осознанная цена: учётные данные не должны меняться незаметно. Удаление спрашивает, что пропадёт, а изменение показывает каждое поле «было — станет» — смену цены или роли видно до сохранения. Создание новых записей не подтверждается: оно ничего не портит. Решение 0034.

**Что будет, если тему потребуется перенести на магазин без алкоголя?**
Алкоголь — признак категории верхнего уровня: только такие позиции получают вид продукции ЕГАИС, крепость, алкокод и МРЦ. Фасовка варианта — объём или масса, а прослеживаемость кодов — два независимых порта, ЕГАИС и «Честный знак». Для сети продуктов с маркировкой «Честного знака» ядро не меняется: ЕГАИС не используется, приёмка по кодам и коробам, проверки при продаже и сверка остаются за «Честным знаком». Решение 0032.

**Почему у артикула нет позиции, а есть вариант?**
Ответ в разделе «Итерация 2»: артикул называет бутылку на полке, у каждого объёма своя цена и свой алкокод. Решение 0031.

## Итерация 4. Регистр движений и учёт марок

**Зачем регистр движений, если можно просто хранить остаток?**
Остаток отвечает на вопрос «сколько сейчас», регистр — «откуда это взялось». Каждое изменение — строка с документом, временем и суммой, поэтому из регистра строятся карточка движения, остаток на любую дату и оборотная ведомость. Остатки хранятся тоже, но как кеш суммы движений, и раз в сутки сверяются с ней (решение 0035).

**Что будет, если две кассы или два кладовщика одновременно возьмут последнюю бутылку или одну марку?**
Проведение блокирует строки остатков и марки в одном и том же порядке, поэтому документы выстраиваются в очередь, а не мешают друг другу. Второй документ увидит, что товара уже нет или марка уже в зале, и получит понятную ошибку. Это проверяет тест с двумя одновременными проведениями, а ограничение БД «остаток не меньше нуля» страхует даже от ошибки в коде.

**Почему деньги хранятся целыми числами?**
Дробные числа с плавающей точкой копят ошибку: 0,1 + 0,2 не равно 0,3. Суммы движений хранятся в копейках, средняя себестоимость — в десятитысячных долях рубля, расчёт идёт на целых с округлением до ближайшего.

**Почему передача пива в зал висит в статусе «Ожидает ЕГАИС»?**
Пиво учитывается в ЕГАИС количественно, по регистрам склада и зала, поэтому перевод надо отразить и там. Учёт в системе меняется сразу, а сообщение в ЕГАИС пишется в очередь в той же транзакции (transactional outbox). Отправит его адаптер к имитатору ЕГАИС — это следующая итерация. В реальной рознице так же: ответ ЕГАИС приходит через минуты, а товар нужен в зале сейчас.

**Как вводятся начальные остатки и почему их проводит руководитель?**
Ввод остатков — первая ревизия: управляющий или кладовщик сканирует товар по зонам, бутылки с марками — по маркам. Оценивается он справочной закупочной ценой, которую видят только руководитель и бухгалтер, поэтому проводят они. Документ один на зону: повторный ввод исказил бы учёт, дальше остатки исправляет только ревизия.

**Как отнести к товару марку нового образца, если в ней нет алкокода?**
Сначала сканируется штрихкод бутылки — система отвечает «выбран товар», а следующие марки относятся к нему. Марка старого образца сама содержит алкокод и находит товар без этого шага. После ввода марка известна системе, и на «Сканере» по ней видно товар, место и всю историю.

**Зачем хранить даже ошибочные сканы?**
Лента сканов объясняет, откуда взялось количество: что засчитано, что не найдено, где оказалась чужая марка. Отменённый скан тоже остаётся, с отметкой. Идентификатор скана присваивает устройство, поэтому повтор запроса после обрыва связи не задвоит количество.

## Итерация 5. Имитатор ЕГАИС и приёмка по ТТН

**Зачем имитатор, если можно было сделать заглушку?**
Заглушка всегда отвечает «принято» и не показала бы ни одного расхождения. Имитатор хранит состояние: знает, у кого какая марка и сколько пива на регистре зала. Поэтому на защите можно показать настоящие отказы: акт с маркой не из ТТН, перевод пива сверх остатка, недоступный УТМ (решение 0037).

**Что будет, если УТМ точки недоступен?**
Документ проводится в учёте, а сообщение остаётся в очереди и уходит само, когда УТМ заработает. В карточке документа видно «в очереди, УТМ недоступен, попыток 3, следующая в 14:05». Это показывается переключателем в интерфейсе имитатора.

**Зачем outbox, если нет брокера сообщений?**
Внешняя система здесь — УТМ, обычный HTTP. Без очереди проведение и отправка — две отдельные записи: при сбое между ними ЕГАИС не узнает о документе или узнает о документе, которого нет. Сообщение пишется в той же транзакции, что и документ, а отправщик забирает его из таблицы с повторами.

**Чем отличаются режимы приёмки?**
«По документу» — факт равен ТТН, сканировать не нужно, только для товара без марок. «По коробам» — сканируется этикетка короба, его содержимое берётся из ТТН. «Выборочно» — так же, но каждый пятый короб вскрывается и считается поштучно: если в нём расхождение, система предлагает пересчитать всё поштучно. «Поштучно» — каждая бутылка и марка. Для продукции с марками разрешены только два последних.

**Почему по коробам система не заметила недостачу во втором коробе?**
Так устроен этот режим: короб считается целым по этикетке. Поэтому для марок он запрещён, а выборочная проверка вскрывает часть коробов, чтобы по ним судить обо всей поставке. Нашлась расхождение во вскрытом коробе — система предлагает перейти к поштучной приёмке.

**Что уходит в ЕГАИС при расхождении?**
Акт расхождения: по каждой позиции — сколько принято и какие марки. Принимается только то, что есть и в ТТН, и в коробах. Непринятые марки ЕГАИС возвращает поставщику, чужие марки и алкоголь не из ТТН не принимаются вовсе.

## Итерация 6. Учебная касса

**Это настоящая касса?**
Нет. Чек учебный и не фискальный: фискализация по 54-ФЗ требует ККТ и оператора фискальных данных, это вне темы работы. Зато всё, что касается учёта, настоящее: проверка времени продажи алкоголя по региону точки, марка в ЕГАИС до выдачи бутылки, разрешительный режим «Честного знака», МРЦ, возраст покупателя, списание с остатка и акт по пиву. Другая кассовая программа может подключиться по тому же кассовому API (`pos.yaml`) — у учебной кассы нет доступа ни к чему, кроме него.

**Как касса входит в систему и чем это отличается от входа сотрудника?**
Касса предъявляет ключ, выданный при регистрации в разделе «Кассы»; в базе хранится только его хеш, и отключённая касса перестаёт работать сразу. Кассир входит на кассе по логину и PIN — быстро и без пароля; пять ошибок подряд блокируют вход на 15 минут. Продавать может только тот, у кого есть право продажи в точке этой кассы (решение 0039).

**Почему чек списывает остаток сразу, а не при закрытии смены?**
Чтобы учёт сходился в любую минуту. Если списывать вечером, то днём проданная бутылка числилась бы и проданной (по марке), и на остатке, и проверка целостности ругалась бы на расхождение. Документ «Продажа» один на смену, а движения пишет каждый чек.

**Что будет, если пробить ту же бутылку второй раз?**
Отказ «Бутылка с этой маркой уже продана. Отложите её и сообщите управляющему». Марка блокируется в транзакции чека, и её статус «продана» не даёт провести её снова — даже если две кассы отправят чек одновременно. После возврата бутылку можно продать снова, поэтому запрет сделан статусом марки, а не уникальным индексом.

**Что если УТМ магазина не отвечает?**
Продажа алкоголя с маркой невозможна — по закону её нужно зафиксировать в ЕГАИС, касса показывает «УТМ магазина не отвечает — продать товар с маркой сейчас нельзя». Остальное продаётся как обычно. Это показывается переключателем в имитаторе.

**А если пропал интернет?**
Касса продолжает продавать товар без марок: каталог с ценами хранится на ней, чек сохраняется в очереди и уходит на сервер, когда связь вернётся. В строке состояния видно «Нет связи» и «Не отправлено: 2». Товар с маркой без связи не продаётся — его проверяют ЕГАИС и «Честный знак». Повторная отправка чека безопасна: идентификатор задаёт касса, сервер не проведёт продажу дважды.

**Касса не доверяет своим часам?**
Нет. Время продажи алкоголя проверяет сервер по местному времени точки и правилам её региона: в Амурской области — с 11 до 21, в Хабаровском крае — с 10 до 22, в дни запрета — весь день. Касса показывает окно продажи в строке состояния, но решение принимает сервер.

**Что происходит при закрытии смены?**
Касса показывает отчёт: чеки, возвраты, выручка наличными и картой. Документ «Продажа» проводится, а проданное за смену пиво уходит в ЕГАИС актом списания из торгового зала — так требует постановление № 2466 для продукции без марок. Забытая открытой смена закрывается сама через сутки.

**Как касса соблюдает цену табака?**
Пачку нельзя продать дороже МРЦ, которую производитель записал в код пачки, и дешевле единой минимальной цены (в 2026 г. — 153 ₽). Касса читает МРЦ прямо из скана: в коде пачки после GTIN и серийного номера 4 символа — это цена в копейках. Если в каталоге цена выше МРЦ пачки, пачка продаётся по МРЦ, а сервер при приёме чека проверяет это ещё раз (решение 0041). Строго равной МРЦ цена быть не обязана: закон запрещает только продажу дороже неё.

**Почему кассы регистрирует и управляющий магазином?**
Касса привязана к магазину, и новую кассу проще подключить на месте. Управляющий видит и регистрирует кассы только своего магазина; администратор — все. Проверку делает сервер, а не интерфейс.

## Итерация 7. Наличие по сети и перемещения

**Как экраны обновляются сами?**
Изменение в базе (документ, скан, остаток, ответ ЕГАИС, чек) объявляет триггер в канал PostgreSQL. Сервер слушает канал и пересылает событие по WebSocket тем, у кого открыт соответствующий экран, а экран перезапрашивает данные. В событии нет данных — только «что изменилось», поэтому права проверяются как обычно. Если соединение обрывалось, после переподключения экран перезапрашивает всё (решение 0042).

**Почему не Kafka или отдельный сервис уведомлений?**
Для 50 пользователей и касс это избыточно: PostgreSQL уже доставляет уведомления всем экземплярам сервера после фиксации транзакции. Модуль событий изолирован, и при росте его можно вынести, не меняя остальной код.

**Что значит «в пути» в карточке наличия?**
Товар отгружен из одной точки и ещё не принят в другой. Он принадлежит сети, но его нет ни на одной полке, поэтому учитывается отдельно. Если при приёмке бутылки не хватило, она остаётся «в пути», пока её не спишут актом с утверждением.

**Почему поступление у получателя появляется сразу при отгрузке?**
В перемещении может быть товар без алкоголя, а ТТН ЕГАИС описывает только алкоголь. Поступление заводится из самого перемещения со всеми строками, а пришедшая ТТН к нему привязывается. Принимают его как обычную поставку — сканированием, с актом расхождения (решение 0044).

**Чем подбираются аналоги?**
Тот же вид продукции и объём, цена в пределах ±15 %, совпадают характеристики, отмеченные в категории как важные для аналогов (например, сырьё водки), и товар есть в текущей точке. Продавец видит, что предложить вместо отсутствующего.

## Итерация 8. Списание и брони

**Почему кладовщик не может сам списать бутылку?**
Списание — частый способ скрыть недостачу или хищение. Поэтому оно вступает в силу только после утверждения другим сотрудником с правом утверждения — не автором и не тем, кто отправил. Пока документ на утверждении, остаток и ЕГАИС не меняются (решение 0045).

**Зачем фото при бое?**
Это подтверждение для руководителя, который утверждает, и для проверяющих. Снимок делается телефоном прямо из документа и уменьшается на устройстве, чтобы не гонять по сети десятки мегабайт.

**Что делать, если марку на разбитой бутылке не читает сканер?**
Выбрать её из списка марок, которые числятся на остатке этой зоны, по видимым последним знакам. Списывается именно эта марка — в ЕГАИС уходит акт по ней.

**Почему сторно есть не для всех документов?**
Поступление, продажа и перемещение уже отражены в ЕГАИС, а акт ЕГАИС не отменяется — его перекрывают встречным документом: возвратом поставщику, возвратом покупателя, обратным перемещением. Сторнировать можно только то, что не вышло за пределы системы, — ввод остатков и передачу в зал без пива.

**Как бронь защищена от случайной продажи?**
Подтверждённая бронь уменьшает свободный остаток (резерв), а марка отложенной бутылки получает статус «отложена». Касса откажет по такой марке и подскажет выдать её через «Брони». Выдача — обычный чек с проверкой возраста и времени продажи, резерв снимается в той же транзакции (решение 0046).

**Что происходит с телефоном покупателя?**
Без его согласия бронь не оформляется. Через 30 дней после закрытия брони имя и телефон обезличиваются фоновой задачей — это требование НЛ-5 и принцип минимизации персональных данных.

## Итерация 9. Ревизия, смартфон как сканер, сверка с ЕГАИС

**Почему ревизия идёт быстрее, чем по бумажной описи?**
Комиссия делится по зонам, и каждый считает свою зону своим телефоном одновременно. Бутылку с маркой не надо записывать и потом сверять: скан сразу говорит «найдена», «переместилась из другой зоны» или «чужая», а прогресс «учёт / факт» по зонам виден всем в реальном времени. Сличительная ведомость готова в момент, когда закрыта последняя зона. На стенде ревизия склада магазина — от создания до отправки на утверждение — укладывается в несколько минут; на настоящей точке время определяется количеством бутылок, а не бумажной работой.

**Что будет, если во время ревизии кассир продаст бутылку?**
Продаст, и это учтут. Магазин на время ревизии не закрывают — так работают алкомаркеты, и это подтвердил заказчик. Учёт при сличении — снимок при старте минус проданное с начала подсчёта; если бутылку посчитали, а потом продали, её вычитают и из факта. Проданная марка не попадёт ни в излишек, ни в «не найдена». В ведомости есть колонка «Продано за подсчёт». Блокируются только приёмка, перемещения и списания по составу ревизии. Остановить и продажи можно флажком «Остановить продажи» — для годовой инвентаризации (решения 0047, 0060).

**Почему недостаточно сравнить количество?**
Количество может совпасть, а бутылки — нет: одну продали без марки в чеке, другую принесли со стороны. Сличение по маркам показывает, какой конкретно бутылки нет — её марка спишется в ЕГАИС, — и какая лишняя: её марку система поставит на баланс, если она нигде больше не числится.

**Что делать с маркой, которую система знает как проданную?**
Такая «чужая» марка на учёт автоматически не встаёт — это повод для разбирательства: возможно, её вернули мимо кассы или продали дважды. Ведомость показывает её отдельно.

**Руководитель не согласен с результатом. Что тогда?**
Он возвращает ведомость с комментарием. Ревизия снова переходит в «Подсчёт»: учёт по-прежнему зафиксирован, нужные зоны открывают или пересчитывают заново, и ведомость отправляется ещё раз.

**Зачем ИНВ-3 и ИНВ-19, если они не обязательны?**
С 2013 года формы можно разрабатывать самим, но бухгалтерии и проверяющим привычны унифицированные. Система выгружает их в PDF для подписи комиссии и в Excel для бухгалтерии.

**Как работает «смартфон как сканер»?**
На ПК кнопка показывает QR-код, кладовщик сканирует его телефоном под своей учётной записью — и дальше каждый скан телефона попадает в документ, открытый на ПК. Код идёт через сервер по тому же каналу событий, что и обновления экранов; на стенде — 55 мс (решение 0048).

**А если пропала связь?**
Скан сохраняется на устройстве и уходит сам, когда связь появится; на экране видно, сколько сканов ждёт отправки. Идентификатор скана создаётся на телефоне, поэтому при повторной отправке сервер не засчитает его дважды (решение 0049).

**Зачем сверка с ЕГАИС, если все документы и так уходят в ЕГАИС?**
Не каждый доходит: акт может быть отклонён, ТТН — не подтверждена, бутылка — продана без марки. Раз в сутки система запрашивает остатки точки в ЕГАИС и показывает только расхождения с подсказкой, что проверить. На стенде сверка сразу нашла марки перемещения, отклонённого ЕГАИС: они числятся у отправителя, а в учёте — «в пути» (решение 0050).

## Итерация 10. Ценники и учёт имущества

**Как магазин узнаёт, какие ценники поменять после переоценки?**
Система помнит, по какой цене в этой точке напечатан каждый ценник. Список «Изменились цены» — товары, которые лежат в торговом зале и у которых текущая цена отличается от напечатанной или ценника ещё не было. Напечатали — товар уходит из списка (решение 0051).

**Почему PDF, а не печать прямо из браузера?**
Размер этикетки и поля в браузере зависят от драйвера, и на термопринтере ценник съезжает. PDF с точными размерами — 66 × 40 мм на листе A4 или 58 × 40 мм на термоэтикетке — печатается одинаково на любом принтере.

**Чем докажете, что штрихкод с ценника читается?**
Тестом: ценник собирается в PDF, PDF растрируется при 300 dpi и распознаётся ZXing — тем же движком, что в сканере камеры. Штрихкод рисуется векторными прямоугольниками, а не картинкой, поэтому не размывается при печати.

**Что на ценнике и почему?**
Наименование, объём и тара, крепость, цена за штуку и за литр, штрихкод, артикул и дата. Цена за единицу измерения — требование правил продажи товаров; объём и крепость покупатель алкоголя ищет первыми.

**Зачем учёт имущества в системе для алкомаркета?**
Холодильник или витрина стоят как сотни бутылок, а при открытии и закрытии магазинов их перевозят. Карточка хранит, где объект стоит, кто за него отвечает и в каком он состоянии, а история — каждое перемещение и смену ответственного с основанием (решение 0052).

**Как проходит инвентаризация имущества?**
Бухгалтер обходит точку со смартфоном и сканирует наклейки. Система сразу показывает три списка: найдено, не найдено и найдено здесь, хотя числится в другой точке. Завершая, найденное из других точек можно перевести сюда — это попадёт в историю объекта.

**Почему инвентаризация имущества — не документ, как ревизия товара?**
Она ничего не меняет в учёте сама: пропавший объект списывают отдельным списанием с утверждением, а чужой — переводят перемещением. Поэтому ей не нужны снимок учёта и утверждение — только сканы и результат.

## Итерация 11. Отчёты, уведомления, дашборд

**Как устроены отчёты, если их двадцать?**
Отчёт — это запись каталога: название, параметры, кому доступен, колонки и запрос. Один движок показывает результат таблицей на экране, выгружает в Excel с формулами итогов и в PDF с реквизитами организации. Новый отчёт — одна запись, без нового экрана (решение 0053).

**Почему кладовщик не видит ABC-анализ, а кассир — чужие продажи?**
У каждого отчёта список ролей из таблицы ТЗ, а точки ограничены правом на отчёты: управляющий видит свою точку, руководитель — сеть. Продавец-кассир видит в «Продажах» и «Сводном отчёте смены» только себя. Это проверяет тест.

**Что значит «тяжёлый отчёт в фоне»?**
Оборотная ведомость или продажи за квартал считаются дольше, чем человек готов ждать у экрана. Такой отчёт ставится в очередь задач, а когда файл готов, приходит уведомление; файл лежит в «Моих отчётах» семь дней.

**Почему фоновые задачи на River, а не по таймеру?**
River держит очередь в той же базе: задача ставится в одной транзакции с данными и не теряется при перезапуске. Главное — при двух экземплярах API периодические задачи выполняет только ведущий, а если он упал, их подхватывает другой. С таймером в каждом процессе брони снимались бы дважды (решение 0055).

**Откуда система знает, кого уведомить?**
Раз в минуту задача проверяет состояние: документы на утверждении, неподтверждённые ТТН, просроченные смены и так далее. Адресаты — все, у кого есть нужное право в точке события, по той же матрице прав, что и для доступа. Ключ события не даёт уведомить человека дважды, а новое уведомление сразу приходит в открытое приложение (решение 0054).

**Что показывает дашборд и как считается оборачиваемость?**
Стоимость запаса, выручку, оборачиваемость в днях, долю неликвида, расхождения с ЕГАИС, неподтверждённые ТТН и бой; графики — выручка по дням, запас по категориям и по точкам. Оборачиваемость — за сколько дней продастся текущий запас при нынешнем темпе: стоимость запаса, делённая на среднюю себестоимость продаж в день.

**Почему «сегодня» в отчётах по Камчатке?**
У сети точки в нескольких часовых поясах, и документ датируется местным днём точки. Если взять дату сервера, вечерние продажи в Петропавловске-Камчатском уже «завтрашние» и выпадут из отчёта. Поэтому «сегодня» по умолчанию — дата на крайнем востоке.

## Итерация 12. Безопасность и эксплуатация

**Зачем второй фактор, если есть пароль?**
Пароль утекает: подсмотрели, записали, подобрали. Администратор может всё, поэтому ему код из
приложения на телефоне обязателен — без телефона украденный пароль бесполезен. Пока второй фактор не
подключён, администратору открыта только страница входа и настроек (решение 0056).

**Как вход по QR-коду не превращается в дыру?**
Код выдаёт только ПК, на котором уже выполнен вход, он живёт 60 секунд и гасится при первом
использовании; в базе хранится хеш. Перехватить код можно, только стоя за спиной сотрудника, — и успеть
за минуту, пока он сам не отсканировал.

**Как сайт сети получит наличие, не получив всего остального?**
Ключом API с областью «наличие»: она открывает несколько операций контракта, любой другой запрос — 403.
Каждое обращение записывается в журнал ключа, отзыв действует сразу (решение 0057).

**Что будет, если упадёт сервер?**
Работают два экземпляра API за Caddy. Упавший исключается по проверке готовности, запросы идут на
второй. Фоновые задачи выполняет ведущий экземпляр, при его отказе ведущим становится другой: на стенде
за 19 секунд, без дублей задач.

**Как быстро восстановитесь из копии?**
Копия делается каждую ночь `pg_dump`, хранится 14 дней. Восстановление на чистой базе демонстрационного
объёма — 2 секунды, норматив — 4 часа; при реальном объёме счёт пойдёт на минуты. Страница «Состояние
системы» показывает дату последней копии, а если копии нет сутки, администратор получает уведомление.

**Выдержит ли система нагрузку?**
Нагрузочный тест — 100 виртуальных пользователей и касс в течение минуты: 95 % запросов быстрее 4 мс,
ошибок нет. Честная оговорка: данные стенда небольшие, на годовом объёме время вырастет, но запас до
нормы 300 мс большой.

**Где стенд?**
Сервер и домен пока не арендованы. Всё для развёртывания готово и проверено локально: образы, compose,
HTTPS через Caddy, копии, выкладка из GitHub Actions — остаётся вписать адрес сервера и домен.

## Итерация 13. Формы ТОРГ и вторая очередь

**Почему ТОРГ-2, ТОРГ-13 и ТОРГ-16, если они не обязательны?**
Как и ИНВ-3 с ИНВ-19, формы с 2013 года рекомендованные, но бухгалтерия и проверяющие привыкли к ним. Все три собраны на одном шаблоне: реквизиты, стороны, таблица, итоги и подписи, — поэтому новая форма — это только описание колонок (решение 0059).

**Что такое XYZ-анализ и зачем он рядом с ABC?**
ABC показывает, что приносит деньги, XYZ — насколько ровно это продаётся по неделям. Товар класса AX — основа ассортимента, его держат всегда; AZ — дорогой, но непредсказуемый, его заказывают осторожно.

**Зачем объёмы в декалитрах, если декларацию розница не подаёт?**
Магазин, который фиксирует продажи в ЕГАИС, декларацию об объёме розничной продажи не подаёт (приказ № 396). Но если точка перестанет фиксировать продажи или запросит проверяющий, сводку по видам продукции в декалитрах получают одним отчётом.

## Нормативная сверка (24.10.2026)

**Где журнал учёта объёма розничной продажи?**
Его отменили с 1 января 2021 г. вместе с приказом Росалкогольрегулирования № 164. Продажи теперь фиксируются в ЕГАИС по постановлению Правительства № 2466: крепкий алкоголь — чеком с маркой при каждой продаже, пиво — актом списания проданного из торгового зала. Поэтому система не печатает журнал, а формирует акт по пиву из чеков смены и отчёт о продажах алкогольной продукции для сверки с ЕГАИС. Розничную декларацию магазин, фиксирующий продажи в ЕГАИС, не подаёт (приказ № 396).

**Почему в ТЗ поменялись реквизиты актов?**
Перед написанием главы 1 каждый источник сверен с действующей редакцией. ЕГАИС теперь регулирует постановление № 2466 вместо № 1459, правила продажи — постановление № 657 (с 1 сентября 2026 г.), инвентаризацию — ФСБУ 28/2023 вместо методических указаний № 49, Data Matrix — ГОСТ ISO/IEC 16022-2025. На учёт в системе это повлияло в одном месте: вместо журнала — акт по пиву и отчёт о продажах.

## Итерация 14. Доработки после проверки заказчиком

**Почему ревизия больше не останавливает продажи?**
Заказчик работал продавцом в алкомаркете: магазин на ревизию не закрывают, даже если сотрудники перегружены. Это же советуют кассовые системы для алкомаркетов и российские руководства по инвентаризации: на время подсчёта останавливают приёмку и перемещения, а продажи сверяют со снимком (решение 0060, там же ссылки).

**Что делать, если ЕГАИС отклонила перемещение?**
Раньше товар «висел» в пути навсегда. Теперь у такого перемещения две кнопки: «Отправить ТТН повторно», если причину устранили, и «Вернуть товар» — остаток и марки возвращаются отправителю, поступление у получателя отменяется (решение 0061).

**Откуда на стенде год продаж?**
Генератор пишет год работы сети через те же регистры, что и настоящие документы: поставки, передачи в зал, чеки касс, бой. Поэтому остатки, себестоимость и марки сходятся, а отчёты показывают сезонность — декабрь выше, январь ниже, пиво растёт летом. На стенде данные пересоздаются каждую ночь (решение 0062).

**Как найти причину медленного запроса или сбоя?**
В Grafana у каждого запроса — трассировка: HTTP, все SQL-запросы и обращения к ЕГАИС и «Честному знаку» одним деревом. Фоновые задачи и обмен с УТМ тоже пишут свои трассировки. Проверено на стенде: запрос кассы виден вместе с проверкой кода в «Честном знаке».

## Итерация 15. Демо-данные и федеральный масштаб

**Откуда ассортимент на стенде, если сеть вымышленная?**
Бренды и производители настоящие — то, что стоит на полке алкомаркета: Русский стандарт, Фанагория, Арарат, Касильеро дель Дьябло, Балтика. Открытого реестра с ассортиментом нет: в Open Food Facts около двухсот российских позиций, а сайты сетей запрещают собирать данные. Поэтому ассортимент описан по брендам, а генератор раскладывает его по объёмам и таре. Цены, штрихкоды и алкокоды вымышленные, но правдоподобные: цены не ниже МРЦ, у штрихкодов верная контрольная цифра — это проверяет сама система при импорте.

**Как показать ревизию, если на защите нет времени считать магазин?**
Командой `task scenario -- stocktake-counting`: ревизия магазина у дома уже идёт, склад посчитан, зал — наполовину. Сценарий выполнил те же действия, что сотрудник на экране, поэтому дальше можно продолжать руками: отсканировать бутылку, закрыть зону, увидеть ведомость. Всего готовых состояний пятнадцать — от ТТН с пересортом до отклонённого ЕГАИС перемещения.

**Выдержит ли система федеральную сеть?**
Проверено на 3000 магазинах в 75 городах России с полными остатками и марками — 53 млн марок, 16 ГБ. Испытание нашло пять дефектов, которых не видно на маленькой сети: «наличие по сети» пересчитывало всю сеть на каждый поиск, отчёт по точке читал журнал всей сети, сканы ревизии взаимно блокировали пул соединений, а события реального времени через NOTIFY выстраивали все коммиты сервера в одну очередь. После исправлений (решение 0064) экраны отвечают за десятки миллисекунд, а один ноутбук, на котором крутятся и генератор нагрузки, и сервер, и база, держит 2 000 одновременно сканирующих кладовщиков с ответом быстрее 0,15 с. При 10 000 запросы встают в очередь, но не теряются. Для федерального внедрения нужен отдельный сервер базы и 4–5 экземпляров API — архитектура это позволяет, общей очереди больше нет.

**Почему «в сети» в «Наличии» может отставать на минуту?**
Остаток по всей сети считается заранее и обновляется раз в минуту: пересчитывать 10 миллионов строк на каждый поиск нельзя. Остаток своего магазина и выбранных точек — живой, по нему продавец и решает, есть ли бутылка.
