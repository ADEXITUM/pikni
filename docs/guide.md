# Пикни: как запустить, потрогать руками и показать

Практическое руководство по локальному стенду: первый запуск, вход под каждой ролью, готовые
сценарии, показ на защите и замеры производительности.

## 1. Первый запуск

Нужны Docker Desktop, Go 1.27, Node.js 24 и [Task](https://taskfile.dev).

```bash
task install            # зависимости фронтенда, один раз
task demo               # демо-данные: восстановить копию из .demo/ (пара минут) или собрать (около часа)
task dev OBS=1          # база, API, имитатор ЕГАИС, сайт и касса + Grafana
task scenario -- all    # во втором терминале: готовые состояния для проверки (1–2 минуты)
```

`task demo` заменяет локальные базы `pikni` и `govsim` копией и перед этим спрашивает. Без `OBS=1`
всё то же, но без Grafana.

| Что | Адрес | Вход |
|---|---|---|
| Рабочее место сотрудника | http://localhost:5173 | логины ниже, пароль `Пикни-демо-2026` |
| Касса | http://localhost:5173/pos/ | кассир по PIN `2468` (касса регистрируется один раз, см. ниже) |
| Имитатор ЕГАИС и «Честного знака» | http://localhost:8090 | любой логин, пароль `govsim` |
| Grafana (метрики, трассировки, журналы) | http://localhost:3000 | `admin` / `admin`, дашборд «Пикни — состояние» |
| Документация API | http://localhost:8080/api/docs | — |

Камера телефона как сканер требует HTTPS: `task dev:https`, затем открыть адрес из консоли с телефона
в той же сети Wi-Fi.

## 2. Кто есть в демо-сети

Сеть «Чекушка»: склады СК-01 (Благовещенск) и СК-02 (Хабаровск), крупные магазины МГ-01, МГ-03,
МГ-04 и магазин у дома МГ-02. Год истории: 1,2 млн чеков, поставки, перемещения, бой.

| Логин | Роль | Что смотреть |
|---|---|---|
| `director` | директор сети | дашборд, отчёты по всей сети, утверждение ревизий и списаний |
| `buh` | бухгалтер | отчёты, себестоимость, формы ИНВ-3 и ТОРГ |
| `admin` | администратор | сотрудники, кассы, ключи API, журнал действий, «Состояние системы» (при первом входе подключит второй фактор) |
| `upr` | управляющий МГ-01 | наличие, ревизия, заявки на перемещение, ценники |
| `keeper` | кладовщик МГ-01 | приёмка, передача в зал, списание, ревизия |
| `kassir` | кассир МГ-01 | касса, брони |
| `upr-mg02` … `upr-mg04`, `keeper-mg02` …, `kassir-mg02` … | сотрудники других магазинов | то же для своей точки |
| `keeper-sk01`, `keeper-sk02` | кладовщики складов | приёмка ТТН от поставщиков, сборка и отгрузка перемещений |

Все логины печатает `task users`. На демонстрационном сервере (`PIKNI_ENV=demo`) на странице входа
есть кнопки быстрого входа под каждой ролью.

## 3. Пройтись руками

**Наличие и поиск.** Под `upr`: «Наличие» — найти «Русский стандарт», открыть карточку: остатки по
всем точкам, похожие товары, карта. Поиск понимает название, артикул (`чк-1`), штрихкод и марку.

**Ревизия.** После `task scenario -- all` под `upr-mg02` в «Документах» идёт полная ревизия:
склад посчитан, зал — наполовину. Можно досчитать зал (камера или поле «Код вручную»), закрыть зону,
перейти к сличению — ведомость с колонкой «Продано за подсчёт». Продажи во время ревизии не
останавливаются.

**Касса.** Под `admin`: «Кассы» → «Зарегистрировать» (точка МГ-01) → открыть ссылку кассы. На кассе
войти `kassir` / `2468`, открыть смену, пробить товар (штрихкод с карточки товара или марку),
закрыть чек. Без связи касса копит чеки и отправляет их, когда сеть вернётся.

**Приёмка ТТН.** Под `keeper-sk02` — поступление с недостачей, пересортом и чужой маркой (сценарий
`ttn-discrepancy`). В имитаторе (http://localhost:8090) видно, что ушло в ЕГАИС и что вернулось.

**Где взять марку для ручного ввода.** `task psql`, затем:

```sql
select e.code, v.article from excise_marks e join variants v on v.id = e.variant_id
join zones z on z.id = e.zone_id join locations l on l.id = e.location_id
where l.code = 'МГ-01' and z.kind = 'floor' and e.status = 'in_stock' limit 5;
```

## 4. Готовые сценарии

`task scenario -- list` — список, `task scenario -- <имя>` — одно состояние, `all` — все. Сценарий
делает то же, что сотрудник на экране, поэтому дальше его можно продолжать руками. Повторный запуск
создаёт новые документы; если мешает уже идущая ревизия, сначала завершите или отмените её
(или `task demo` — вернуть чистую копию).

| Сценарий | Под кем смотреть | Что показать |
|---|---|---|
| `stocktake-draft` | `upr` | «Начать подсчёт» |
| `stocktake-counting` | `upr-mg02` | досчитать зал, сличение |
| `stocktake-reconciling` | `upr-mg03` | ведомость: не найдены, переместилась, чужая марка |
| `stocktake-approval` | `director` | утвердить ревизию пива с недостачей |
| `transfer-requested` | `keeper-sk01` | согласовать заявку магазина, собрать сканами, отгрузить |
| `transfer-in-transit` | `keeper` | принять поступление по перемещению поштучно |
| `transfer-rejected` | `keeper-sk02` | ЕГАИС отклонила ТТН: «Отправить повторно» или «Вернуть товар» |
| `writeoff-approval` | `director` | бой ждёт второго ключа: утвердить с фото |
| `reservation` | `kassir` | продать бронь на кассе |
| `ttn-incoming` | `keeper-sk01` | принять ТТН по коробам |
| `ttn-discrepancy` | `keeper-sk02` | приёмка с расхождениями и акт |
| `ttn-overdue` | `keeper-sk01` | уведомление «ТТН не подтверждена» |
| `price-below-mrc` | `upr` | цена ниже МРЦ: уведомление, касса не пробьёт |
| `utm-down` | `director` | УТМ недоступен: уведомление и оповещение Grafana |
| `egais-mismatch` | `upr` | «Сверка с ЕГАИС» — расхождение по пиву |

## 5. Показ на защите (10–12 минут)

1. **Директор** (`director`): дашборд — выручка, продажи по сезонам, недостачи; отчёт «Продажи
   алкогольной продукции» за год — 1,2 млн чеков, несколько секунд (дашборд — около 1,5 с).
2. **Управляющий** (`upr`): «Наличие» — бутылки нет в своём магазине, есть в соседнем; заявка на
   перемещение в один клик.
3. **Ревизия при открытом магазине** (`upr-mg02`, сценарий `stocktake-counting`): досчитать зал с
   телефона, параллельно пробить на кассе бутылку из этой же зоны — сличение учтёт продажу.
4. **Касса**: продажа марочной бутылки, QR-код ЕГАИС на чеке; отключить сеть — чек уходит позже.
5. **ЕГАИС**: в имитаторе — ТТН с пересортом; приёмка показывает расхождение; отклонённое
   перемещение — «Вернуть товар».
6. **Надёжность и масштаб**: Grafana во время `task load` — запросы в секунду, время ответа,
   соединения. Цифры федерального испытания — в протоколе (П-33) и решении 0064.

## 6. Производительность и Grafana

Дашборд «Пикни — состояние» (http://localhost:3000, `task dev OBS=1`) обновляется каждые 10 секунд.

| Панель | Что значит |
|---|---|
| Запросов в секунду, по маршрутам | нагрузка на API целиком и по операциям |
| Время ответа p95 (GET и POST) | 95 % запросов быстрее этого значения |
| Доля ошибок 5xx | ошибки сервера; оповещение — выше 1 % |
| Запросов в обработке | очередь внутри API: растёт, когда сервер не успевает |
| Соединения с базой (занято / свободно / предел) | занято = предел — пул исчерпан, запросы ждут |
| Ожидания свободного соединения | как часто запрос ждал соединение с базой |
| Чеки и сканы в минуту, сканы в секунду | бизнес-нагрузка: касса и ревизии |
| Очередь в ЕГАИС, УТМ недоступен | обмен с ЕГАИС по точкам |

В Grafana → Explore → Tempo видна трассировка любого запроса: HTTP, все SQL-запросы и обращения к
ЕГАИС и «Честному знаку» одним деревом. В Loki — журнал с тем же `trace_id`.

**Замеры:**

```bash
task load                      # 80 сотрудников и 20 касс на демо-сети, минута; итог — таблица p50/p95/p99
task load DURATION=5m          # дольше, чтобы посмотреть графики

task federal:build             # один раз: федеральная сеть на 3000 магазинов в отдельной базе (~40 мин, 16 ГБ)
task federal:api               # API на федеральной базе на :8081 (метрики — в тот же Grafana)
task load:stocktake SCANNERS=2000   # во втором терминале: 2000 кладовщиков сканируют при ревизии
task load:stocktake SCANNERS=10000  # предел: на ноутбуке стенд упирается в процессор
```

Ориентиры, полученные на ноутбуке разработки (генератор нагрузки, API и база на одной машине):

- обычная работа на демо-сети: p95 около 4–30 мс;
- на федеральной сети — p95 27 мс;
- 2000 сканирующих — 1300 сканов в секунду, p95 0,13 с;
- 10 000 — 1465 сканов в секунду, ответы встают в очередь (5,7 с), но не теряются.

Подробности — в протоколе испытаний (П-33) и решениях 0063 и 0064.
