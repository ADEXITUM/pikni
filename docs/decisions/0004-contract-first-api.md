# 0004. API от контракта

**Статус:** принято, 22.10.2026.

**Контекст.** Клиентов у сервера три: приложение сотрудников, касса, справочная страница. Плюс внешние системы через ключи API. Сервер и клиенты не должны расходиться.

**Решение.** Источник правды — `openapi/pikni.yaml` (OpenAPI 3.0.3):
- **сервер:** oapi-codegen генерирует модели и strict-интерфейс для Echo v5. Обработчик получает разобранный запрос и возвращает типизированный ответ, а строка `var _ apispec.StrictServerInterface = (*API)(nil)` не даёт собрать сервер, если операция не реализована;
- **фронтенд:** openapi-typescript генерирует типы, openapi-fetch делает запросы с проверкой путей и ответов;
- **ошибки** — RFC 9457 (`application/problem+json`), заголовки по-русски, подробности 5xx не раскрываются;
- **списки** — в обёртке `{"items": [...]}`.

**Последствия:**
- **плюс:** изменение контракта ломает компиляцию на обеих сторонах, а не работу у пользователя;
- CI проверяет, что сгенерированный код совпадает с контрактом;
- **минус:** модели БД и API — разные структуры, между ними есть маленькая функция перевода. Это граница: таблица может меняться, не ломая контракт.

**Отвергнуто:**
- **писать обработчики и типы вручную;**
- **обычный (не strict) echo-server:** больше ручного разбора, компилятор не следит за форматом ответа;
- **OpenAPI 3.1:** генератор поддерживает его не полностью.
