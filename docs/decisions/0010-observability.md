# 0010. Наблюдаемость на OpenTelemetry и стеке Grafana

**Статус:** принято, 22.10.2026.

**Контекст.** Нужно видеть, что происходит в системе:
- путь запроса через компоненты;
- скорость ответов в сравнении с ТЗ;
- ошибки, доступность УТМ;
- журналы, связанные с конкретным запросом.

**Решение:**
- **приложение пишет трассировки, метрики и журналы по стандарту OpenTelemetry** и отправляет их по OTLP/HTTP:
  - Echo — официальный `echo-opentelemetry`;
  - pgx — `otelpgx`, плюс метрики пула;
  - журнал — `log/slog` в stdout с `trace_id` и в OpenTelemetry через мост `otelslog`;
- **хранение и просмотр** — `grafana/otel-lgtm`: коллектор, Prometheus, Loki, Tempo и Grafana в одном контейнере;
- **без адреса OTLP телеметрия выключена:** тесты и CI работают без коллектора;
- **дашборды и оповещения** хранятся в репозитории, появятся в итерации 12.

**Последствия:**
- **проверено:** трассировка `GET /api/v1/locations → SELECT ListLocations → pool.acquire`, строки журнала находятся по `trace_id`, метрики HTTP разбиты по маршрутам;
- **стандарт OpenTelemetry:** хранилище меняется настройкой коллектора, код не трогаем;
- **минус:** стек занимает около 1,5 ГБ памяти, поэтому сервер на 8 ГБ.

**Отвергнуто:**
- **Datadog и другие облачные сервисы:** платные, оплата из России затруднена, персональные данные ушли бы за рубеж (152-ФЗ);
- **сбор журналов отдельным агентом из stdout:** ещё один сервис в сопровождении.
