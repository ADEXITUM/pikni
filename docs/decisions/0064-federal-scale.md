# 0064. Федеральный масштаб: что сломалось на 3000 магазинах и как исправлено

**Статус:** принято, 25.10.2026. Частично заменяет решение 0042: события реального времени идут через
таблицу, а не через NOTIFY.

**Контекст.** Нагрузочное испытание на федеральной сети (решение 0063): 2996 магазинов и 82
распределительных центра, 53 млн марок, 10,6 млн строк остатков, 16 ГБ. На демо-сети всё работало
быстро. На федеральной нашлись пять дефектов, которые на маленьких данных не видны.

**Найдено и исправлено:**
1. **«Наличие по сети» суммировало остатки всей сети на каждый поиск** — 10,6 млн строк, больше
   10 с на запрос; соседние экраны тормозили до 8 с. Сеть теперь считается заранее в
   материализованном представлении `network_stock` и обновляется раз в минуту фоновой задачей.
   Остаток своей точки и выбранных точек остаётся живым, его берут по индексу точки. Стало 10–70 мс;
   фильтр «весь город Москва» (около 800 магазинов) — 0,6–1,5 с.
2. **Отчёт по точке читал журнал движений всей сети:** индекса по точке не было. Добавлен индекс
   `stock_moves (location_id, doc_date)`.
3. **Кэшированный план отчётов не использовал этот индекс.** Условие «точки не выбраны или точка из
   списка» в общем плане подготовленного запроса читает всю таблицу, а PostgreSQL переходит на общий
   план после нескольких выполнений. Отчёты выполняются безымянным запросом (`DescribeExec`), план
   строится под выбранные точки: 44 мс вместо тайм-аутов.
   - Отчёт на экране ограничен 20 с с подсказкой «выберите точки или выгрузите файлом».
   - Выгрузка по сети больше 50 точек строится в фоне, как тяжёлые отчёты за длинный период.
4. **Взаимная блокировка пула соединений при сканировании.** Скан ревизии блокировал документ в
   транзакции, а справочник и марку читал через общий пул, то есть ждал второго соединения. Под
   нагрузкой все соединения заняты теми, кто ждёт ту же блокировку: 99,8 % запросов падали по
   тайм-ауту. Справочники и марки внутри транзакций документов теперь читаются через её соединение
   (`withTx`).
5. **NOTIFY выстраивал коммиты в очередь на весь сервер.** Каждый скан объявлял событие реального
   времени через `pg_notify`, а коммиты с NOTIFY PostgreSQL выполняет по одному. Потолок был около
   500 сканов в секунду на всю систему, сколько ни добавляй серверов. Триггеры теперь пишут события
   в нежурналируемую таблицу `realtime_events`. Каждый экземпляр API забирает новые события раз в
   200 мс и перечитывает последние номера, чтобы не пропустить транзакцию, зафиксированную позже
   соседней. Таблица хранит события минуту.

6. **Год истории демо-сети** (1,2 млн чеков): дашборд директора открывался 3,5 с. Дата чека по часовому
   поясу точки индексом не ищется, и продажи за период читали все чеки. Добавлены индексы по времени
   чека и по товару в строках чеков, запросы получили условие по времени с запасом в сутки. Дашборд —
   1,4 с; годовые отчёты по миллиону строк — 4–8 с.

**Результат на одном ноутбуке** (16 потоков; генератор нагрузки, API и PostgreSQL на одной машине):

| Сотрудников сканируют одновременно (скан в ~1,5 с) | Сканов/с | p50 | p95 | Ошибки |
|---|---|---|---|---|
| 1 500 | 988 | 16 мс | 29 мс | 0 |
| 2 000 | 1 303 | 23 мс | 131 мс | 0 |
| 2 500 | 1 451 | 213 мс | 391 мс | 0 |
| 10 000 | 1 465 | 5,4 с | 5,7 с | 0 |

При 10 000 стенд упирается в процессор (92 %): запросы ждут в очереди, но ни один не теряется —
1,15 млн сканов записаны в 500 ревизиях. Смешанная нагрузка на чтение (100 пользователей и касс на
федеральной базе) — p95 27 мс, ошибок 0; до исправлений было p95 около 8 с и 26 % ошибок.

**Последствия:**
- **плюс:** скорость поиска наличия и отчётов по точке не зависит от размера сети;
- **плюс:** сканирование масштабируется добавлением экземпляров API и сервера базы: общей очереди
  коммитов больше нет;
- **минус:** «в сети» в «Наличии» отстаёт от учёта до минуты; своя точка и выбранные — без отставания;
- **минус:** событие реального времени приходит с задержкой до 200 мс вместо мгновенной.

**Отвергнуто:**
- **счётчик остатка по сети, обновляемый каждым движением:** тысяча магазинов, продающих одну
  позицию, ждали бы блокировки одной строки;
- **отказ от событий реального времени при ревизии:** живой прогресс зон — то, ради чего комиссия
  считает с телефонов (решение 0047).

**Для федерального внедрения** (по замерам): 10 000 одновременно сканирующих — около 6 700 сканов в
секунду. Это отдельный сервер PostgreSQL и 4–5 экземпляров API за балансировщиком. Обмен с УТМ
опрашивает точки по очереди, его нужно распределить по экземплярам (решение 0063).
