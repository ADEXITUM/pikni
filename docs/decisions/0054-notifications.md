# 0054. Уведомления по состоянию данных, а не из каждого модуля

**Статус:** принято, 24.10.2026.

**Контекст.** Центр уведомлений (УВ-2): поступила ТТН и она не подтверждена в срок, заявка на перемещение, товар отгружен или прибыл, бронь создана или истекает, документ ждёт утверждения, расхождение с ЕГАИС, УТМ недоступен, смена не закрыта, отчёт готов, остаток ниже минимума.

**Решение:**
- **правила по состоянию:** фоновая задача раз в минуту выполняет запросы-правила («документы на утверждении», «ТТН в черновике дольше N часов»…). Модули не знают про уведомления — новое правило добавляется в одном месте;
- **адресаты** — по матрице прав: у пользователя должно быть право события в его точке (например, `docs.approve` для утверждения). Автор заявки о своей же заявке не уведомляется;
- **без дублей:** у события ключ (`approve:<документ>:<версия>`), уникальный для пользователя. Повторная отправка на утверждение — новая версия, новое уведомление;
- **доставка сразу:** триггер на вставку публикует событие в личную тему `user:<id>` канала реального времени (решение 0042); подписаться на чужую тему нельзя — сервер сверяет её с сеансом;
- **окно** — правила смотрят на события последних суток-двух, чтобы при первом запуске не завалить людей старым;
- **срок для ТТН** — настройка `ttn_reminder_hours` (по умолчанию 24 часа).

**Последствия:**
- **плюс:** уведомление не теряется, даже если событие пришло мимо API (ТТН из ЕГАИС, автозакрытие смены);
- **минус:** задержка до минуты для правил; «отчёт готов» отправляется сразу из задачи.

**Отвергнуто:**
- **вызов «уведомить» в каждом сервисе:** десяток мест, легко забыть, и событие от ЕГАИС пришлось бы ловить отдельно;
- **Web Push на смартфон:** вторая очередь (УВ-3).
