# 0039. Кассовый API: ключ кассы, PIN кассира, чек проводится сразу

**Статус:** принято, 24.10.2026.

**Контекст.** Касса работает отдельно от приложения сотрудников (КС-6): у неё своя аутентификация и своя автономная работа. Продажа товара с маркой должна быть подтверждена ЕГАИС до выдачи товара, а остаток и учёт марок не должны расходиться ни на минуту, иначе ревизия и проверка целостности покажут ложные расхождения.

**Решение:**
- **два уровня входа.** Касса предъявляет ключ, выданный при регистрации (`Authorization: Device pos_<префикс>_<секрет>`); в базе — только SHA-256 секрета, префикс виден в списке касс. Кассир входит по логину и PIN (4–6 цифр, argon2id, как пароль), получает токен сессии кассы (`X-Cashier-Session`) на сутки. Пять неверных PIN подряд блокируют вход на 15 минут. Продавать может только тот, у кого есть право `pos.sell` в точке кассы — проверка та же матрица ПБ-6;
- **отдельный контракт** `openapi/pos.yaml` и отдельный сгенерированный сервер (`posspec`): кассе не нужен остальной API, а другой кассовой программе — понятный короткий протокол;
- **смена открывает документ «Продажа»** по торговому залу; **каждый чек проводится сразу**: движения в регистре, марки → «продана», а не одной суммой при закрытии смены. Так `stock_integrity()` в любой момент сходится: проданная бутылка уже не числится на остатке;
- **товар без марок продаётся сверх остатка** — недостача уходит в «недостачу к разбору» (решение 0013), как и задумано для кассы;
- **чек с марками синхронно отправляется в УТМ** (таймаут 3 с) внутри транзакции проведения. Отказ ЕГАИС или недоступный УТМ — отказ продажи (422 с кодом и текстом для кассира), транзакция откатывается, марка остаётся на остатке;
- **коды «Честного знака»** проверяются перед продажей (разрешительный режим), а выбывают после коммита: продажа уже состоялась, повтор вывода безопасен;
- **все проверки повторяются при приёме чека**: время продажи алкоголя по местному времени точки, марка, код, МРЦ, подтверждение возраста. Касса могла проверить устаревшие данные;
- **идентификатор чека задаёт касса** (UUID): повторная отправка после обрыва связи возвращает уже принятый чек;
- **закрытие смены** проводит «Продажу» и ставит в очередь ЕГАИС акт списания из торгового зала «Реализация» по проданному пиву (нетто за вычетом возвратов). Смена, открытая больше суток назад, закрывается сама при следующем обращении;
- **возврат** — только по чеку продажи этой точки и не больше проданного за вычетом прежних возвратов; марка возвращается на остаток, в ЕГАИС уходит чек возврата.

**Последствия:**
- **плюс:** двойная продажа марки невозможна без отдельного индекса: марку блокирует строка `excise_marks` в той же транзакции, а статус «продана» не даёт продать её второй раз. Поэтому уникального индекса по `mark_code` в строках чеков нет — после возврата ту же бутылку можно законно продать снова;
- **плюс:** УТМ недоступен — касса продолжает продавать товар без марок, а продажа алкоголя с маркой честно отказывает с понятной причиной;
- **минус:** вызов УТМ внутри транзакции держит блокировку марки до 3 секунд; для одной кассы это незаметно. Если ЕГАИС принял чек, а коммит не прошёл, повтор того же чека имитатор примет как уже известный;
- **отложено:** МРЦ табака (максимальная цена с пачки) — в имитаторе ещё нет источника; уведомление об автозакрытии смены — с центром уведомлений (итерация 11); загрузка каталога изменениями, а не целиком.

**Отвергнуто:**
- **списывать остаток при закрытии смены:** весь день марки числились бы «проданными» при нетронутом остатке, и проверка целостности ложно сообщала бы о расхождении;
- **уникальный индекс марки в строках чеков:** запретил бы повторную продажу возвращённой бутылки;
- **сессии кассира в общей таблице `sessions`:** у них другой способ входа, другой срок и нет CSRF; отдельная `pos_sessions` проще.
