# 0016. Две роли базы данных и журнал только на добавление

**Статус:** принято, 23.10.2026.

**Контекст.** Журнал действий (ПБ-7) не должен изменяться через интерфейс, а лучше — вообще никем. Если приложение подключается к базе владельцем таблиц, ошибка в коде или SQL-инъекция может удалить таблицу или отключить её защиту.

**Решение:**
- **`pikni_owner`** владеет базой и таблицами; под ним работает только мигратор (`DATABASE_MIGRATOR_URL`);
- **`pikni_app`** — роль приложения: только `SELECT`, `INSERT`, `UPDATE`, `DELETE`, выданные заранее через `ALTER DEFAULT PRIVILEGES` на все будущие таблицы владельца;
- **роли создаёт скрипт первичной настройки кластера** (`api/db/initdb/10-roles.sh`), а не миграция: роль — объект всего кластера, её создаёт суперпользователь;
- **у `pikni_app` отозваны `UPDATE` и `DELETE` на `audit_log`**;
- **триггер `forbid_change`** отклоняет изменение, удаление и `TRUNCATE` журнала даже для владельца. Функция общая и пригодится регистру движений (итерация 4).

**Последствия:**
- **плюс:** две независимые защиты: правами (ошибка 42501) и триггером (ошибка P0001); тесты проверяют обе;
- **плюс:** приложение не может менять схему: создавать, удалять таблицы, отключать триггеры;
- суперпользователь базы по-прежнему может всё: защиту от администратора СУБД дала бы только цепочка хешей или вынос журнала во внешнее хранилище — это за рамками работы.

**Отвергнуто:**
- **одна роль для всего:** любая ошибка приложения получает права владельца схемы;
- **только проверка в коде:** обходится прямым SQL;
- **роли в миграциях:** мигратору понадобились бы права суперпользователя.
