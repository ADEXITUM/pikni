# 0014. Сессии на сервере, а не JWT

**Статус:** принято, 23.10.2026.

**Контекст.** Сотрудникам нужен вход в браузере на ПК и смартфоне. Администратор должен блокировать сотрудника и завершать его сеансы сразу, а сотрудник — видеть свои сеансы и завершать чужие устройства (ПБ-5). Сервер один — модульный монолит; все копии ходят в одну базу.

**Решение:**
- **токен сессии** — 128 случайных бит в cookie `pikni_sid` (HttpOnly, Secure, SameSite=Lax, Path=/api); в таблице `sessions` хранится только SHA-256 токена;
- **срок** — 12 ч бездействия и 7 суток всего; отметка последнего обращения обновляется не чаще раза в 5 минут, чтобы не писать в базу на каждый запрос;
- **каждый запрос** ищет сессию в базе одним запросом вместе с пользователем и его точками;
- **выход, блокировка, сброс пароля** удаляют строки сессий — доступ пропадает со следующего запроса;
- **кеш сессий в памяти отложен:** сейчас запрос к базе по уникальному индексу занимает доли миллисекунды. Если понадобится, кеш будет в памяти каждой копии со сбросом через `LISTEN/NOTIFY`, без Redis.

**Последствия:**
- **плюс:** отзыв доступа мгновенный и простой — это удаление строки;
- **плюс:** токен недоступен JavaScript страницы, поэтому XSS не может его украсть;
- **плюс:** утечка дампа базы не даёт войти — в ней только хеши;
- минус: каждый запрос обращается к базе;
- cookie отправляется браузером автоматически, поэтому нужна защита от CSRF (решение 0021).

**Отвергнуто:**
- **JWT:** подпись проверяется без базы, но отозвать выданный токен до истечения срока нельзя без списка отозванных — то есть без той же базы. Преимущество JWT — проверка в разных сервисах без общего хранилища — монолиту не нужно;
- **токен в localStorage:** доступен любому скрипту на странице;
- **Redis для сессий:** вторая система хранения ради того, что PostgreSQL делает достаточно быстро (решение 0003).
