# 0055. Фоновые задачи на River вместо таймеров в процессе

**Статус:** принято, 24.10.2026. Развивает решение 0003.

**Контекст.** До итерации 11 периодическая работа шла горутинами с таймером: снятие просроченных броней, ежедневный запрос остатков ЕГАИС. С двумя экземплярами API (раздел 7 ТЗ, отказ экземпляра) каждая задача выполнялась бы дважды. Появились отчёты в фоне и уведомления.

**Решение:**
- **River** (очередь задач на PostgreSQL): задача ставится в той же транзакции, что и данные, и не теряется при перезапуске;
- **схема River** — миграция goose, сгенерированная из `rivermigrate` (версии 1–8): тестовые базы и стенды получают её вместе с остальной схемой;
- **периодические задачи** — уведомления и снятие броней раз в минуту, очистка «Моих отчётов» и запрос остатков ЕГАИС раз в час. River выбирает ведущий экземпляр, поэтому задача выполняется один раз; если ведущий упал, её подхватит другой. Уникальность по интервалу не даёт задачам копиться;
- **по запросу** — формирование отчёта: API ставит задачу клиентом «только вставка», выполняет её клиент фоновых задач.

**Последствия:**
- **плюс:** второй экземпляр API не удваивает работу, повторные попытки и журнал задач — из коробки;
- **минус:** ещё восемь таблиц в базе; обмен с УТМ пока остаётся горутиной — он идемпотентен по статусу сообщения.

**Отвергнуто:**
- **cron в контейнере:** нет транзакционной постановки и выбора ведущего;
- **брокер сообщений (RabbitMQ, NATS):** отдельный сервис, а задачи и так рядом с данными (решение 0003).
